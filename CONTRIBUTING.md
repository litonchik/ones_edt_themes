# Участие в разработке

## Сообщение об ошибке

Создайте Issue с версией плагина, точной сборкой EDT, ОС/архитектурой,
версией JVM, выбранной палитрой и шагами воспроизведения.
Для проблемы с цветами приложите снимок на примере без рабочих данных.
Укажите, меняется ли результат после перезапуска и в чистой тестовой workspace.
Удалите из логов пароли, токены и содержимое рабочих проектов перед публикацией.

## Сборка и проверки

Для unit tests достаточно JDK 17 и Maven:

```shell
mvn --batch-mode --no-transfer-progress -f tests/unit/pom.xml clean test
```

Модуль проверяет чистую Java-модель и ресурсы палитр без Eclipse/EDT.
Та же команда настроена в `.github/workflows/unit-tests.yml`.
Первый запуск GitHub Actions проверяется после публикации репозитория.

Полная сборка выполняется на Windows через `scripts/build.ps1 -Action Verify`
с параметрами `-JavaHome`, `-MavenHome`, `-EdtHome` (пример в [README](README.md)).
Используйте Maven **3.9.11**, JDK **17** и EDT **2026.1.3+25**.
Maven 3.10.0 с текущим Tycho 4.0.13 в локальной среде не работает.
Сборка пишет только в каталоги проекта; ПО устанавливается разработчиком отдельно.

Runtime-проверки выполняются исключительно в отдельной копии EDT и тестовой
рабочей области. См. [проверки MVP](docs/testing/mvp-validation.md) и
[последний целевой отчёт](docs/testing/visual-studio-dark-validation.md).
Скрипты p2/workbench не предназначены для рабочей EDT пользователя.

## Изменения

- Сохраняйте исходные значения настроек, включая отсутствие явного override.
- Не меняйте persisted IDs палитр, personal keys и snapshot format без миграции.
- Используйте публичные API; vendor JAR и рабочую установку EDT не патчите.
- Для палитры указывайте первичный источник, commit, лицензию и адаптации 17 ролей.
- Проверяйте затронутое поведение соразмерно изменению. Не выдавайте unit tests за runtime.
- Сопровождайте изменение кратким описанием результата, проверок и ограничений.

Сборки находятся в игнорируемом `dist/`; в PR включаются исходники,
документация и необходимые проверочные артефакты. Отобранные отчёты и снимки
в `docs/testing` сохраняются как история проверок. Временные данные идут в `.work`.
Исторические материалы `docs/superpowers` остаются архивом; Superpowers в проекте не применяется.

Отправляя собственные изменения, вы предлагаете их под MIT проекта.
Для сторонних материалов сохраняйте отдельную лицензию и атрибуцию.
