# Светлые панели интерфейса

Дата реализации: 04.11.2026, локальный кандидат 0.1.22.

В EDT штатная Dark связывает общие SWT-контролы с named colors,
а Light почти не содержит соответствующих правил. Поэтому правильные RGB
в реестре сами по себе не подтверждают окраску навигатора и свойств.

## Область применения

`LightUiStyles` задаёт локальные inline CSS-значения отдельным обычным
контролам рабочего окна: контейнерам, деревьям, таблицам, полям, спискам,
подписям, ссылкам и заголовкам вкладок. Используются SWT `Widget.setData`
для CSS-данных и `IThemeEngine.applyStyles`; обращения к классам из
ограниченных `x-friends` пакетов не требуются. Также поддерживается собственная
страница параметров плагина. Остальные диалоги EDT этим обходом не охвачены.
Новые CSS theme IDs и глобальный stylesheet не регистрируются.

Контейнеры используют `panel`, деревья/таблицы/поля — `editor.background`,
текст — `text`, ссылки — `accent`, недоступный текст — `disabled`.
Выбранная вкладка отличается от панели фоном `editor.background`,
разделители используют `border`. Новые роли и preference keys не добавляются.

Корни содержимого всех реализованных `IEditorPart` определяются через
публичные `MPart` и `IWorkbenchPartSite.getService`. Их поддеревья исключены
целиком: общие UI-правила не проникают в BSL, сравнение, конструкторы,
предпросмотр форм, макеты и произвольные редакторы. Графические Canvas
в панелях также исключены; разрешены только обычные CLabel и Hyperlink.
Если корень открытого редактора пока нельзя определить, обход окна
не добавляет новые классы. Проверка исключения произвольного редактора
не заменяет ручную проверку настоящего metadata-проекта и макетов.

CSS-данные и inline-стили существуют только в памяти при активной известной светлой палитре.
При восстановлении или переходе к Dark они снимаются с сохранением
исходных и добавленных сторонними компонентами классов и inline-стилей
(включая отсутствие значения). Фильтры Paint,
Resize и Show обновляют новые контролы; при остановке плагина фильтры снимаются.

## Порядок применения цветов

Перед штатным переключением CSS собственные классы и inline-значения
снимаются. После восстановления точных preferences реестр получает их
текущие RGB. Для контролов из них формируются **буквальные HEX**, а не ссылки
на named colors: конвертер Eclipse может кэшировать служебное `RGB(0,1,2)`
или прежний цвет до завершения переключения. Для выбранных вкладок также
используются публичные SWT `setSelectionForeground/Background`.
Читается текущее явное значение, включая последующее ручное изменение;
новая собственность над настройкой не захватывается. Прежний механизм
восстановления четырёх factory colors сохранён.

Внешняя Light без активного профиля не получает этих правил. Vendor JAR,
глобальные настройки Java и рабочая установленная EDT не изменяются.

## Источники и границы

Первичные локальные источники от 04.11.2026: `com._1c.g5.v8.dt.theming.ui`
(`css/light/edt-light_basestyle.css`, `css/dark/edt-dark_globalstyle.css`,
`css/dark/edt-dark_tabstyle.css`), исходники Eclipse `WidgetElement`,
`ControlElement`, `CompositeElement`, `CSSSWTColorHelper`,
`AbstractCSSEngine.applyInlineStyle`, `WorkbenchThemeManager`,
`ColorAndFontProviderImpl` и зарегистрированные
CSS-свойства в `org.eclipse.e4.ui.css.swt/plugin.xml`.
Код использует публичные API; внутренние исходники прочитаны для диагностики,
их классы напрямую не вызываются и reflection не используется.
Общий механизм CSS и widget data описан в [документации Eclipse Platform UI](https://github.com/eclipse-platform/eclipse.platform.ui/blob/master/docs/CSS.md)
(просмотрена 04.11.2026); конкретные data keys и обработка inline-поля `style`
дополнительно сверены с локальными исходниками и проверяются на трёх целевых EDT.

Фактическая матрица: [проверка 0.1.22](../testing/light-ui-validation.md).
Нативные кнопки/полосы прокрутки могут сохранять оформление ОС; после смены
Light/Dark по-прежнему рекомендуется перезапуск. Для старых BSL merge panes
сохраняется ограничение на переоткрытие. macOS этой доработкой не проверена.
