# Просмотр и редактирование палитры на странице тем

Дата: 14 октября 2026. Статус: анализ возможности по запросу пользователя,
рекомендации для следующей доработки; реализация и новый UI не выполнялись.
Пользователь хочет видеть, какие цвета выбранного стиля где используются,
и менять их под себя. Текущая поставка — 0.1.3.

## Подтверждено по проекту и целевой платформе

- Palette содержит 17 обязательных ролей, RGB задан в формате #RRGGBB.
- PaletteCatalog загружает встроенные Darcula/Monokai из ресурсов bundle.
  Пользовательских вариантов и сохранения overrides пока нет.
- SettingCatalog связывает роли с 51 цветовой настройкой. Дополнительно есть
  5 флагов SystemDefault: всего 56 записей в карте.
- ThemeCoordinator и preview независимо загружают встроенную палитру.
  Для редактирования оба должны получать один разрешённый набор цветов.
- SnapshotService сохраняет первоначальные значения и защищает последующие
  внешние ручные правки. Его applyExplicit сейчас принимает весь набор ключей,
  поэтому применение этого метода ко всему профилю затёрло бы чужие ручные правки.
- Отдельная карта 56 штатных preference values служит сохранению состояния,
  затронутого самой Dark. Это не 56 дополнительных ролей нашего профиля.
- javap публичных классов установленной EDT подтвердил наличие ColorSelector
  и ColorDialog с выбором/чтением RGB. Новое системное ПО не требуется.

Локальные источники: `Palette.java`, `PaletteCatalog.java`, `SettingCatalog.java`,
`SnapshotService.java`, `ThemeCoordinator.java`, `ThemePreferencePage.java`,
`resources/palettes/*.properties`, `resources/edt-2026.1-settings.properties`.
Подробная карта и ограничения: [настройки EDT](../reference/edt-2026.1-settings.md).

Цель проверки: установленная EDT 2026.1.3+25 Windows x64, Eclipse 4.30.0,
SWT 3.124.200, Java 17.0.18. javap запускался по полному пути из Axiom JDK 17,
установленная EDT использовалась только для чтения.

Первичные внешние источники, просмотрены 14.10.2026:
[JFace ColorSelector](https://help.eclipse.org/latest/rtopic/org.eclipse.platform.doc.isv/reference/api/org/eclipse/jface/preference/ColorSelector.html)
описывает кнопку с образцом и штатным диалогом выбора цвета;
[SWT ColorDialog](https://help.eclipse.org/latest/topic/org.eclipse.platform.doc.isv/reference/api/org/eclipse/swt/widgets/ColorDialog.html)
описывает получение RGB и возврат null при отмене. Документация latest дополняет
локальное подтверждение API, не заменяет проверку именно целевой версии.

## Варианты

| Вариант | Возможности | Объём/ограничения |
|---|---|---|
| Только просмотр | Образцы, HEX и объяснения применения | Самый небольшой; не выполняет пожелание о настройке |
| Редактор 17 ролей — рекомендуется | Пользовательские цвета внутри Darcula/Monokai, сохранение, preview и сброс | Умеренная доработка UI, хранения и применения; сохраняет связи стиля |
| Редактор каждого target | Раздельно менять, например, BSL builtins и UI accent | Более сложный UI и второй слой overrides; легко потерять согласованность стиля |

## Рекомендуемое поведение

На той же странице добавить раздел «Палитра» с группами «Код» и «Интерфейс».
Группа не должна дублировать одну общую роль в двух независимых редакторах.
Строка показывает русское имя, цветной образец, HEX, признак пользовательской
правки и пояснение «Где используется». Для общей роли пояснение перечисляет
все затрагиваемые области. Подробности targets берутся из карты, а не из
ручной второй копии preference IDs.

ColorSelector/ColorDialog выбирает цвет; отдельный HEX input при необходимости
даёт точное значение с проверкой формата. Ошибка ввода не допускает Apply.
Для BSL применять пояснение «BSL выключен — правка сохранится, но к редактору
BSL сейчас не применяется». Редактор профиля доступен для Darcula/Monokai;
«Штатное оформление» сохраняет текущую семантику выхода из профиля.

До Apply/OK изменения обновляют локальный образец кода и образцы интерфейса.
Реальные окна EDT не перекрашиваются при каждом выборе цвета. Для интерфейсных
ролей одного текущего BSL preview недостаточно: нужны локальные примеры панели,
границы, обычного/неактивного текста и состояний. Это будет иллюстрация ролей,
а не обещание точного вида всех специфических экранов EDT.

Правки хранить как отдельные overrides выбранного профиля в preferences плагина
на уровне workspace. Эффективная палитра = встроенная палитра + её overrides.
Darcula и Monokai независимы. После обновления встроенные ресурсы не перезаписывают
личные значения. Экспорт/импорт и создание дополнительных стилей можно отложить.

Черновики обеих палитр сохраняются при переключении внутри открытого диалога.
Apply/OK сохраняет изменённые профили и применяет только выбранный профиль;
Cancel отбрасывает ещё не сохранённые черновики. После Apply последующий Cancel
не откатывает уже применённое — как в текущей версии.

Два разных действия должны иметь разные подписи:

- «Вернуть цвет стиля» / «Сбросить правки палитры» удаляет overrides и возвращает
  встроенную Darcula/Monokai после Apply/OK.
- «Восстановить исходное оформление» возвращает EDT к состоянию до включения
  плагина. Сохранённые личные варианты палитр остаются для повторного выбора.

## Существенные условия реализации

1. Снимок первоначальных цветов нельзя заменять отредактированной палитрой.
   Хранение пользовательского профиля и журнал восстановления — разные состояния.
2. Явная правка роли через плагин должна переопределять соответствующие targets,
   но не возвращать под управление все остальные настройки, вручную изменённые
   через штатную EDT. Требуется применение с набором явно изменённых ключей,
   а не вызов существующего applyExplicit для всего плана.
3. Значения профиля могут отличаться от фактических colors при внешних ручных
   overrides или настройках проекта. UI должен показывать эту ситуацию и не
   выдавать палитру профиля за аудит всех эффективных цветов редакторов.
   Восстановить единое значение роли можно её явным редактированием/сбросом.
4. Preview, списки и coordinator должны разрешать одну и ту же палитру. Нельзя
   оставить preview на PaletteCatalog.load, когда Apply использует overrides.
5. Сохранение overrides и применение EDT должны согласованно обрабатывать ошибку
   flush/частичный отказ/перезапуск. Неуспешный Apply не объявляется сохранённым
   профилем; нужен rollback либо журнал завершения соответствующих операций.
6. При BSL=false не менять исходные BSL значения. Шрифт независим. Прикладной вид
   формы/MXL/графической схемы/СКД не входит в редактор палитры.
7. После override/reset повторно проверить доступность текста и selection в Dark,
   освобождение SWT ресурсов, размер страницы и повышенный DPI. Желательно
   предупреждать о плохом контрасте, сохраняя возможность сознательного выбора.

## Оценка и проверка

Предварительная инженерная оценка, не обязательство по времени:
просмотр существующей палитры — порядка 1–2 часов;
редактор ролей с сохранением, сбросом, защитой ручных правок и проверенным p2 ZIP —
порядка одного рабочего дня (ориентир 4–8 часов). Полный target editor существенно
расширяет объём. Главная работа — семантика применения и восстановления, не picker.

Нужны meaningful unit tests для merge/reset/валидации RGB и изоляции профилей,
выборочного explicit apply, исходных absent/explicit values и отказа сохранения.
В копии EDT — preview без записи, переключение черновиков, Apply/OK/Cancel,
BSL=false, обе палитры, штатные ручные изменения, restart, восстановление,
а затем p2 install/uninstall/audit. Старые журналы должны оставаться совместимыми.

Фактической runtime-проверки этой новой функции пока нет. Текущие успешные проверки
0.1.3 подтверждают базу для доработки, но не реализацию будущего редактора.
